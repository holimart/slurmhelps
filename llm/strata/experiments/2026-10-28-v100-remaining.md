## R2 — NVLink / P2P

### Hardware

`nvidia-smi topo -m` is **NV2 for all six pairs** (bonded NVLinks); every GPU
reports six 25.781 GB/s links and P2P `OK` in `topo -p2p r/w`. The driver's
`nvidia-smi nvlink --help` *lists* `-gt d` throughput counters, but on this
V100 node every link reports `Data Tx: N/A / Data Rx: N/A` — the counters are
**not available on V100**, so 0.000 MiB from `-gt d` is *not* evidence of
zero traffic. Transport had to be established by call tracing.

`p2pbench` (256 MiB, 20 iterations, CUDA events, the engine's own
`libcudart.so.12`, explicit `cudaDeviceEnablePeerAccess`):

| test | GB/s |
|:--|---:|
| local D2D (HBM sanity) | 407.97 |
| peer 0→1 (same NUMA pair) | **48.50** |
| peer 0→2 (cross NUMA pair) | **48.50** |
| `cudaMemcpyAsync(Default)` 0→1 | **48.50** |
| D2H (PCIe, one direction) | 13.15 |
| H2D (PCIe, one direction) | 12.41 |
| GPU0 → pinned host → GPU1 | 12.77 |

Peer copies are **3.8× the host route**, identical for same-NUMA and
cross-NUMA pairs, and `cudaMemcpyAsync(Default)` between peer-enabled devices
takes the same 48.5 GB/s — i.e. the runtime does route it over NVLink once
peer access is on. The 48.5 GB/s plateau is the per-copy-engine limit of a
256 MiB `cudaMemcpyPeerAsync`, not the link limit: the hardware is
6 × 25.781 ≈ 150 GB/s per direction (the node's aggregate is often quoted as
~155 GB/s/GPU).

### Engine transport

`strata launch` exposes **no** peer/P2P flag. The engine's own help has
`--peer-device`, explicitly *not* combinable with a layer split
(*"Not with --layer-split or --expert-cache-device1..3"*), so on the 4× split
there is no supported switch that would move the stage hand-off to NVLink.
`STRATA_PEER_NO_P2P=1` is the only P2P switch the engine reads; it targets the
peer-experts tier.

Three-cell A/B at window 32,768, C1, 2 requests each (same recipe, clean
probe clamped to the real window):

| run | TTFT | decode | aggregate | prompt tokens |
|:--|---:|---:|---:|---:|
| default | 10.52 s | 71.7 tok/s | 10.42 tok/s | 64,259 |
| with copy trace (shim) | 10.33 s | 82.5 tok/s | 10.61 tok/s | 64,322 |
| `STRATA_PEER_NO_P2P=1` | 10.20 s | 79.9 tok/s | 10.68 tok/s | 64,387 |

Differences are run-to-run noise (TTFT 3 %, decode ±15 %, aggregate 2.5 %).
Turning P2P off changes nothing because the layer split does not use it.

The copy trace inside the cell window (25 s, both requests) is decisive:

| call | calls | bytes | endpoints |
|:--|---:|---:|:--|
| `cudaMemcpyAsync(D2D)` | 44,952 | 2,768 MB | **same device** on every call |
| `cudaMemcpyAsync(H2D)` | 104 | 8,980 MB | host → GPU |
| `cudaMemcpyAsync(D2H)` | 30 | 8,278 MB | GPU → host |
| `cudaMemcpyAsync(Default)` | 696 | 1,732 MB | GPU → host (unregistered) |
| `cudaMemcpyPeerAsync` / `cuMemcpyPeerAsync` | **0** | **0** | — |
| `cudaDeviceEnablePeerAccess` / `cuCtxEnablePeerAccess` | **0** | — | — |

`cudaPointerGetAttributes` on every source and destination finds **no copy
with two known device endpoints on different GPUs**, and the engine never
enables peer access by either the runtime or the driver API. The symmetric
~8.3 GB D2H / ~9.0 GB H2D are the stage hand-off going **through host memory**
(the engine's "prompt path's streamed ring"); the 86 GB of H2D in the
whole-run trace is weight/KV fill. Since no peer access is ever enabled, the
engine cannot read or write a peer card's memory, and the layer split is
confined to PCIe even though the cards are wired NV2.

Two checks close the only loophole. Every copy returned 0, and a
`cudaMemcpyAsync(Default)` between two GPUs requires peer access — so the
unattributed (`-2`) destinations cannot be peer cards. And if the runtime had
chosen an internal host staging for such a copy, those bytes would still cross
PCIe, never NVLink. Either way, no stage hand-off is a peer transfer.

**Verdict.** NVLink is present and fast — a 256 MiB `cudaMemcpyPeerAsync`
sustains **48.5 GB/s** versus **12.4 GB/s** host→device, and
`cudaMemcpyAsync(Default)` between peer-enabled devices takes the same
48.5 GB/s — but the 4-GPU layer split **does not use it**. Inter-stage traffic
is a host ring over PCIe; the engine's 12.4 GB/s figure is both its probe and
the real hand-off cost. The ~150–155 GB/s of NVLink per GPU is idle in this
configuration. This is actionable: the 2×-vs-4× decode advantage at C1 seen
on 2026-10-27 (fewer hand-offs) is consistent with a PCIe-bound hand-off, and
putting the hand-off on peer copies would need an engine change, not a flag.

## R3 — clean 262k stability

45-minute loop at C1: each iteration is a unique-salt **cold** 262k turn
(full prefill) followed by a byte-identical **warm** prompt (one initial turn
plus two repeats). One JSON line per request, exact HTTP body on failure,
plus 1 Hz power and per-iteration RAM/VRAM.

The first attempt (main job) reproduced the old defect at 100 % and gave the
exact reason:

```text
HTTP 400: request exceeds the context window: prompt (262214 tokens) leaves
no room to answer in the context (262144); requests are never truncated
```

With `max_tokens=128` and the probe's default 128-token safety, the target was
261,888 and the calibration error (~320 tokens at 262k) pushed the real
prompt past the window on every request (19,420 rejections in 45 min).

Rerun with **`--pad-safety 2048`** (target 259,968; real prompt 259,539):

| quantity | value |
|:--|---:|
| iterations | 27 |
| requests | 105 |
| **errors** | **0** |
| cold TTFT p50 | 69.77 s (67.93–70.94) |
| cold TTFT drift (first 3 → last 3) | **+0.23 %** (slope −13 ms/iter, noise) |
| cold decode p50 | 67.7 tok/s |
| warm TTFT p50 | 2.23 s (0.45–3.13) |
| warm reused tokens p50 | 259,534 |
| prompt tokens p50 | 259,539 |
| min MemAvailable | 274 GB |
| max VRAM used (per GPU) | 24,144 MiB |
| GPU power mean / p50 / p90 / max | 206.7 / 252.4 / 296.6 / 364.2 W |
| GPU utilisation mean / p50 | 70.6 % / 91 % |
| SM clock p50 | 1500 MHz |
| temperature mean / max | 59.7 / 68 °C |

The 10/96 HTTP 400s from the previous soak are therefore a **probe margin
bug, not engine instability**: with a 2,048-token safety there are zero
errors and no TTFT drift over 45 min. The first warm turn of iteration 1 is a
full 71 s prefill; from iteration 2 onward the warm prompt is served from the
conversation cache at ~1.3 s (first turn) / ~2.2 s (repeats), with the whole
259.5k-token prefix reused.

## Runner defects found and fixed

1. `local ... out=...$label` in the R1 helper expanded before `label` was
   assigned; under `set -u` it aborted the whole batch right after staging
   (job 38248605).
2. `/tmp` is shared across jobs on volta05 and the first attempt left it
   full; ENOSPC then failed every launch (38249052). The runner now removes
   only its own stale trees, stages packs sequentially, and reclaims the
   per-phase private data dir.
3. `verify_recipe` required `--batch 1`, which the engine omits at
   parallel=1, so healthy servers were rejected (38249188). The batch token
   is now skipped at p=1 and a failed recipe check is an audit warning.
4. A fixup script referenced an undefined `I3S2` (38340488/38340527).
5. The fixup's 1:30 wall expired before it published, losing node-local
   cells (38340538); the job now publishes per phase and from an EXIT trap.

## Caveats

- One run per cell; 2 cold NIAH repeats per position; one tool canary per
  context. Quality is one needle and one tool shape.
- Coder at 262k is a 4× result: the 2× launch timed out in the launcher, not
  in the engine, and was not retried a third time.
- R2's transport evidence is call-level (LD_PRELOAD on the runtime and driver
  peer entry points), not hardware counters: V100's `nvidia-smi nvlink -gt`
  returns N/A. A driver call made through `dlsym` would evade the shim; the
  absence of any peer access is also consistent with the symmetric host
  round trip and with `STRATA_PEER_NO_P2P` having no effect.
- The 48.5 GB/s peer number is a copy-engine figure; a load/store kernel
  could show more of the 150 GB/s, but the node's only `nvcc` is CUDA 13.4,
  which no longer emits sm_70.
- Power is GPU-only (`power.draw` sum), not wall power; the node's CPUs, fans
  and PSU losses are excluded.
- R3 covers 45 min and 27 cold prefills; it does not exercise C2 or eviction
  pressure from multiple conversations.

## What remains genuinely unmeasurable here

- **MI50 / MI100**: not present in `ffa-gpulab` (the AMD measurement in this
  campaign is a separate 2× MI210 job); no allocation can produce those
  numbers.
- **Vast.ai 3090**: requires Vast credit, which we do not have.
- **NVLink link saturation** (as opposed to copy-engine throughput): no
  sm_70-capable compiler on the node.
- **Hardware NVLink counters on V100**: the driver reports N/A.
