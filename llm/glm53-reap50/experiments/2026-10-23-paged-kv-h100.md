# 2026-10-23 — paged-KV on 2× H100 80 GB (stock vLLM)

Stock vLLM 0.32 + REAP50 NVFP4 v2 on `hopper01` (2× H100 80 GB, 160 GB).
This is the H100 comparison to the working 2× A100 fork run.

## Configuration

- Host venv `/work/.../venvs/vllm032py`, vLLM 0.32.0, Python 3.12.15.
- `GLM-5.3-Flash-REAP50-NVFP4-v2`, TP2, BF16 KV, block size 128.
- `FLASHMLA_SPARSE` attention, Marlin NVFP4 W4A16 linear + MoE
  (H100 has no native FP4), prefix caching, eager mode, 4,096 batched tokens,
  8 max sequences, `gpu_memory_utilization=0.94`.
- The dense layers 0–2 use the checkpoint-config ignore from the A100 fix.

H100 is **not** pure stock-kernel path in this environment. Two host issues had
to be worked around:

1. `uv` Python 3.12.15 with headers (the system 3.12 lacks `Python.h`, which
   Triton JIT needs).
2. DeepGEMM JIT found no `nvcc` on PATH. `CUDA_HOME=/usr/local/cuda-13.4`,
   `JIT_NVCC_COMPILER`, and PDL off fixed that; TileLang 0.1.12 also emitted
   `tl.pdl_sync`/`tl.pdl_trigger` opcodes its bundled compiler did not lower,
   so mHC uses the native torch implementation instead of the TileLang path.

The native mHC fallback preserves correctness but is not the stock TileLang
performance path. The prefill numbers are useful; the decode numbers are
likely pessimistic versus a working stock kernel build.

H100 wins on prefill/TTFT by ~1.2–1.5× over A100. The A100 fork currently
wins on decode and has slightly more KV capacity, but is an older vLLM fork.
llama.cpp on 2× L40S is far behind on prefill and has no multi-sequence paged
KV capacity.

## Caveats / not measured

- **Single-sequence reuse only.** No multi-session shared-prefix tree, no
  per-agent resident capacity, no eviction-under-concurrency test.
- H100 decode is affected by the native mHC fallback and Marlin W4A16.
- No H2D/RAM-tier attribution.
- No SGLang comparison: SGLang v0.5.22 has no SM80/SM89 GLM-5.3 DSA path and
  does not support this A100 route; H100 SGLang was not attempted after stock
  vLLM worked.
