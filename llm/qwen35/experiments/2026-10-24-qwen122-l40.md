# 2026-10-24 — Qwen3.5-122B-A10B on L40 (attempt)

Goal: run the 122B Qwen checkpoint on a **four-L40 48 GB** node and measure
the same smoke matrix.

## Availability

The four-L40 nodes are `fuuk-13`, `fuuk-14`, `fuuk-15`. At the time of the
attempt all were fully allocated:

```text
fuuk-13  ALLOCATED  cpu=192/192  mem=1400G  gres/gpu:l40=4
fuuk-14  ALLOCATED  cpu=192/192  mem=1400G  gres/gpu:l40=4
fuuk-15  ALLOCATED  cpu=192/192  mem=1400G  gres/gpu:l40=4
```

They were running another user's long CPU jobs, so there was **no free
four-L40 node**. I did not preempt that user's job.

## Fallback: 2× L40

An idle two-L40 node (`uk-g6-02`) was used as a partial check:

```text
job 38143629
uk-g6-02
2× L40 48 GB, TP2
model: Qwen3.5-122B-A10B-AWQ-4bit
max_model_len=262144
```

The server initialised the API, tokenizer and NCCL group, then the TP workers
disappeared during model startup. It never opened port 8003:

```text
curl http://uk-g6-02:8003/health -> connection refused
nvidia-smi -> 0 MiB / 0 MiB
```

The job hung with the engine waiting for its workers and was cancelled. The
log contained no explicit Python exception, so this is either a worker OOM
(75 GB of 4-bit weights across 2×48 GB with KV/activation headroom) or an
SM89 kernel/loader issue. It is **not** a performance result.

## What is not measured

- 122B on **4× L40 192 GB** — no node was available.
- 122B speed on L40 — the 2× fallback never reached ready.
- 35B on L40 — not attempted in this run.

Likely next steps:

1. Retry 122B on a genuinely free 4× L40 node; 75 GB / 4 = ~19 GB weights per
   GPU, much safer than 2×.
2. If 4× still fails, test 35B on one L40 to separate “L40 SM89 kernel
   support” from “122B capacity”.
3. Keep the A100 122B path as the validated reference.

The A100 Qwen server was left running separately; this L40 job was cancelled
and `uk-g6-02` returned to idle.
