## Blockers on SM90

1. **CSF experts run only on b12x.** Every layer with `weight_scale_encoding: csf`
   gets `Nvfp4CsfMoEMethod` (`model_executor/layers/quantization/modelopt.py:1851-1860`),
   and that method always builds a `B12xExperts` kernel
   (`model_executor/layers/quantization/nvfp4_csf.py:381`). There is no Marlin or
   Triton fallback for CSF experts. b12x MoE requires
   `current_platform.is_device_capability_family(120)`
   (`model_executor/layers/fused_moe/b12x.py:775-783`), and the b12x package
   gate is `is_b12x()` = capability `(12, 0)` or `(12, 1)` only
   (`flashinfer/experimental/b12x/_lib/gating.py:28-31`). The b12x GEMMs are
   CuTe-DSL SM120 warp-MMA kernels (`_lib/dense_gemm.py` imports
   `cutlass.utils.blackwell_helpers`, `nvfp4_pair_to_bf16x2_sm120`).
2. **The NVFP4 PLE table loads only on b12x.** On the non-b12x path,
   `Qwen4ExpPLEEmbeddingMethod.from_quant_config` raises
   `NotImplementedError("PLE format 'nvfp4' requires the b12x execution backend")`
   (`models/qwen4_exp/nvidia/ngram_embedding.py:161-165`). It accepts only
   bf16 and fp8 tables. The b12x PLE (`B12xNGramEmbedding`) sits behind the
   same SM120/121 gate.
3. **The b12x backend cannot be enabled selectively.** `uses_b12x()`
   (`models/qwen4_exp/nvidia/backend.py`) is true as soon as `--linear-backend` or
   `--moe-backend` is `b12x`, and it then switches QSA attention, hyperconnection
   and PLE to b12x as a set (`models/qwen4_exp/nvidia/model.py:240,255,426,709,891`).
   The b12x linear kernels also reject non-SM12x devices
   (`model_executor/kernels/linear/nvfp4/b12x.py:244`).

## What would work on SM90 (for whoever unblocks this)

- **Plain NVFP4 / W4A16_NVFP4 / MXFP8 linears and MoE run through Marlin.**
  `ModelOptMixedPrecisionConfig.get_min_capability() == 75` (modelopt.py:1623-1633),
  and Marlin supports MXFP8 on SM80+ (modelopt.py:1170).
- **The rest of the qwen4_exp model has SM90 code.** The non-b12x model path
  has SM90 kernels: low-latency GEMM plans `QWEN4_EXP_SM90_GEMM_PLANS`
  (`models/qwen4_exp/nvidia/low_latency_gemm.py:85,151-159`), FlashAttention-varlen
  QSA (`nvidia/qsa.py`), the cooperative top-k indexer for SM90
  (`nvidia/ops/qsa_indexer.py:486`), and the pinned-host PLE with UVA
  (`nvidia/ngram_embedding.py:651-657`, `EngramConfig.cpu_offload`).

There are therefore two ways forward:

- **(a) A different vLLM build.** It needs a non-b12x `Nvfp4CsfMoEMethod`
  (decode the CSF scales to plain E4M3 block scales at load, then use the Marlin
  W4A16 MoE) and an NVFP4 PLE table on the non-b12x path (dequant at lookup,
  like `Qwen4ExpPLEFp8EmbeddingMethod`).
- **(b) A converted checkpoint for this container's non-b12x path.** Re-encode
  the CSF expert scales as plain ModelOpt NVFP4 (one E4M3 scale per 16 weights,
  so at most 0.5625 B per expert weight, a few GiB more than CSF), and store the PLE table as fp8 (about 51 GB of pinned host RAM, which
  the Engram CPU offload supports). Serve it with `--linear-backend auto
  --moe-backend auto`, without `--gdn-decode-kernel b12x`, without the
  `B12X_*`/`CUTE_DSL_ARCH=sm_120a`/`TORCH_CUDA_ARCH_LIST=12.0a` environment, with
  BF16 KV, and with MTP off at first. That is new engineering plus a
  quality check, not a configuration change.

## Resources (for when it is unblocked)

- **GPU:** about 68 GiB of non-PLE weights over TP2 is about 34 GiB per H100,
  which leaves about 35 GiB per GPU for KV/state at 0.90. Qwen4Exp is hybrid:
  only 12 of 48 layers are full attention, the rest GDN. 262K context should fit.
- **Host:** the PLE table is 26.8 GiB pinned (TP-sharded,
  `b12x_ple.py:345-346`). Add two TP workers and an API server at about
  10-15 GiB each and loader staging. `config-hopper.json` requests **96G**,
  not 220G.
- **hopper01 today:** RealMemory 1014000 MB and AllocMem 901120 MB, so about
  110 GB is requestable. A 220G request would pend; 96G fits now.
